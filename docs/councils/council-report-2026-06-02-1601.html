LLM Council · Architecture Decision

Drafting in n8n vs the Bridge

Hermes / Dubriani — live WhatsApp yacht-charter booking system · 5 advisors → anonymized peer review → chairman synthesis · 2026-06-02

The question put to the council

Should the main message-drafting (first draft + REFINE + REGEN) be moved out of the n8n workflow and into the Python bridge — stay in n8n — or go hybrid?

A — Consolidate drafting into the bridge  ·  B — Keep it in n8n (status quo)  ·  C — Hybrid: n8n orchestrates but calls one thin bridge /draft endpoint so the prompt + catalog + NO_INVENT live in exactly one place.

Context: catalog currently duplicated across a ~70KB n8n prompt node + the bridge's system-prompt.md (hand-synced). Recurring problem: drafter invents off-catalog prices/specs. Bridge has working draft code + pytest + git; n8n has no test harness. 2-vCPU box, load-sensitive. Gold-conversation retrieval designed-but-unbuilt (bridge-side). One-operator team, live revenue path, human approves every draft.

CHAIRMAN'S VERDICT
Validator first, then the reversible flagged endpoint, then retrieval. The majority answer (consolidate to a thin /draft endpoint) is the right architecture — but the council was solving the stated problem (fabricated prices) only by assumption. Build a programmatic catalog validator (cheap, curative, also fixes the rubber-stamp approval gate), then migrate via the Executor's flag-gated, load-railed, first-draft-only plan — not the Expansionist's all-in move. Reject the claim that relocation "kills hallucination at the root."

Where the Council Agrees

Four of five land on a thin-endpoint / consolidation answer, and the diagnosis is near-unanimous: a catalog living in two hand-synced places is structurally rotten, and NO_INVENT buried in a 70KB blob is low-salience. The real convergence is narrow: put prompt + catalog + NO_INVENT in one artifact the bridge owns, expose it as a /draft endpoint, and do not move 32 nodes of orchestration onto the fragile box.

⚠ Treat this consensus with suspicion. Every reviewer independently flagged "two copies → drift → hallucination → consolidate" as a shared story, not evidence. A model fabricates "375 AED fine dining" perfectly well from a single flawless catalog — fabrication is a generation behavior, not only a sync artifact. Consolidation is correct housekeeping; the council has no data that it touches the recurring symptom at all.

Where the Council Clashes

A genuine three-way split on how to weigh compounding upside against blast radius on a fragile one-operator system:

  • Expansionist (all-in A): move everything; the prize is gold-retrieval grounding drafts in real booked conversations + the gate loop wrapping every draft "for free." Dismisses the box: "drafting is I/O-bound, you're awaiting."
  • Contrarian (STAY unless…): days of surgery on a live revenue path to fix drift a 10-line CI diff also kills; and a naive hybrid puts a multi-call synchronous gate loop on a 2-vCPU box that already melted + already timed out once. Only proceed with a price validator + async/poll + concurrency cap + n8n fallback built first.
  • Middle (First Principles + Executor + Outsider): one artifact, thin endpoint, keep orchestration in n8n — with the Executor adding the rails the Expansionist waved off.

The Expansionist's "I/O-bound" claim is the weakest link — the gate loop is 2-3 sequential calls that serialize against payments/scoring/identity-merge on two cores. The Contrarian's load analysis is correct; his "STAY" is too conservative only because the Executor shows the migration can be made reversible and load-safe.

Blind Spots the Council Caught

The most valuable findings emerged only in peer review:

  1. No invent-rate baseline — nothing is logged. No labeled set of fabricated-price incidents, no measured rate. Any fix ships blind; "better" is unfalsifiable.
  2. Nobody diffed the two catalogs. The whole consensus rests on "drift causes the hallucinations," yet no one ran the cheapest test — diff the n8n Build Prompt node against system-prompt.md — to confirm drift is even happening.
  3. REFINE/REGEN co-migration risk. REFINE edits an operator-approved draft; move it carelessly and you can silently re-invent a price a human already blessed.
  4. The human approval gate is itself failing. A human approves every draft yet invented prices ship often enough to be "the recurring problem." No source-of-truth refactor fixes a reviewer who doesn't catch "375 fine dining." Surface a validator verdict to the human.
  5. A programmatic validator beats relocation for the actual problem. A regex/lookup checking every price/spec/yacht-name against the 104-entry catalog and hard-rejecting unknowns stops fabrication regardless of where the prompt runs. It exists in neither place today. (The Contrarian's lone-dissenter point — three reviewers said he broke ranks correctly.)

The Recommendation

Do not start with the migration. Start with measurement and the validator — then do the Executor's flagged thin-endpoint consolidation, not the Expansionist's all-in move. The tie-breaking variable is what a catalog diff and an invent-rate log actually show; until then every architecture choice bets on an unconfirmed diagnosis.

  1. The validator is the highest-leverage fix and nearly free. A post-draft check (every price/spec/yacht-name must exist in the 104-entry catalog, else hard-reject + force regen). ~A day in the bridge's existing pytest harness, and its verdict can be surfaced to the human approver — fixing the rubber-stamp gate at the same time. The actual cure for the actual disease.
  2. Then consolidate via the Executor's plan. One artifact (system-prompt.md), kill the 70KB duplicate, expose _anthropic_draft + _gate_loop behind a flagged /draft endpoint, first-draft only, DRAFT_VIA_BRIDGE env flag, watch ten live drafts, rollback = flip flag false. Load rails are mandatory: in-process semaphore (max 1-2 concurrent gate loops), hard ~25s timeout returning a typed "retry" that never sends empty, fallback to the n8n draft path.
  3. REFINE/REGEN migrate later, same flag pattern, only after first-draft proves out — with an explicit check that REFINE can't re-invent a price in an already-approved draft.
  4. Reject the Expansionist's framing that relocation "kills hallucination at the root" and that the box is a non-issue. Retrieval is a real prize and the bridge is its right host — but it's step N, behind the same validator and load rails.

The One Thing to Do First

Diff the two catalogs right now — the n8n "Build Prompt" node against the bridge's system-prompt.md — and grep your logs / approved-draft history for the specific fabricated values (e.g. "375") to get a first invent-rate count. One command's worth of output decides everything downstream: if they've drifted, consolidation is urgent; if they're identical, the model is fabricating from a clean source and the validator — not the migration — is the whole ballgame.

The five advisors (full responses)
The Contrariandownside / what fails

Option C (Hybrid) is the only defensible answer — but first kill A. The hallucination is your bleeding wound, not architecture elegance: the model invents the same "375 AED fine dining" whether the prompt ships from a jsCode node or a /draft endpoint. The real fix is a programmatic post-draft validator that regexes every price/spec/yacht-name against the 104-entry catalog and hard-rejects unknowns — and you have it in neither place today. Don't let a migration masquerade as a quality fix. The trap in C: a synchronous Anthropic call behind /draft on a 2-vCPU box that already melted and ate one Anthropic timeout; a draft + ≥8 gate loop is 3-5 sequential calls serializing against payments/scoring/identity-merge. Mitigation must be explicit: async job + poll, hard concurrency cap, timeout-fallback returning the n8n draft. Payback: one operator, live revenue path, and the win is "one catalog instead of two you verified in-sync today anyway" — days of surgery for drift a 10-line CI diff also kills. Do C only if you build the validator + async/fallback first. Otherwise STAY.

The First Principles Thinkerreframe the problem

Drafting is not the problem. Drift is. The system proved the cause today: catalog + NO_INVENT live in two places, hand-verified in sync — and "verified in sync today" admits nothing structurally keeps them in sync. You're one busy week from a silent fork, and the failure mode is exactly the recurring symptom. Hallucination here isn't random; it's the model reading a 70KB blob where NO_INVENT is buried at low salience. The real question isn't "where should drafting run," it's "where does the single source of truth live, and what reads it." The answer collapses: ONE prompt artifact, and everything that drafts or scores reads it. That makes B indefensible. Between A and hybrid: you don't need to move orchestration, retry logic, Telegram cards, or 32 nodes onto a load-sensitive box. The bridge already owns system-prompt.md and _anthropic_draft — expose exactly that as a thin /draft endpoint. n8n keeps orchestrating; the 70KB node dies; the catalog exists once; the unbuilt retrieval feature now has a host.

The Expansionistupside / what compounds

Move it into the bridge (A) and you stop running a 70KB string through a jsCode node and start running a real software asset. The big unlock is gold-conversation retrieval — designed, bridge-side, structurally impossible to feed the n8n drafter today. The moment drafting lives in the bridge, retrieval plugs into _anthropic_draft; grounding every first-draft in real past booked conversations kills off-catalog hallucination at the root via live exemplars of correct pricing. Conversion follows grounding. Second unlock: _gate_loop + _anthropic_score wrap the MAIN draft for free — auto-regen-until-quality on every message. Third: one prompt, git-versioned, pytest-covered; A/B prompts, per-yacht upsell, multilingual, price-feed auto-sync all ship as tested Python diffs instead of manual API PUTs against an unversioned node. Hybrid leaves drafting split across two runtimes forever; retrieval/gating stays a reach-around. Go A. The box is 2-vCPU but drafting is I/O-bound on the Anthropic call — you're awaiting, not CPU-burning.

The Outsidercurse-of-knowledge check

The catalog living in two places, hand-synced, is the thing that jumps out. A 70,000-character prompt with "don't invent things" buried in it, plus a parallel copy of 104 prices in a Python file — two copies of the same truth maintained by one person by hand. That's a guarantee they drift, and "the AI invents a price" is exactly what drift looks like; I'd bet some "hallucinations" are just the two copies disagreeing. Why does the catalog exist twice at all? One source of truth isn't an architecture debate, it's hygiene. Every asset lives Python-side except the drafting itself — keeping drafting in the visual tool looks like inertia, not a decision. One thing nobody says out loud: a human approves every draft, yet the AI still ships invented prices often enough to be "the recurring problem" — your reviewer is rubber-stamping fake numbers. And the dumb question: why is the entire 104-item catalog in the prompt instead of looked up for the specific boat being discussed?

Peer-review highlights
What the 5 anonymous reviewers found

Unanimous biggest blind spot: the Expansionist — sells migration as a hallucination cure and waves off the 2-vCPU load ("I/O-bound, you're awaiting") when the gate loop is 2-3 serialized calls on a box that already melted/timed out. Most ambitious, least operationally honest.

Agreement not to trust: "two copies → drift → hallucination → therefore consolidate." A satisfying shared narrative, but the model can fabricate from a single perfectly-synced catalog. Only the Contrarian broke ranks correctly — the validator, not relocation, is the actual fix.
