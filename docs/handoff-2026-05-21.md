# Handoff — 2026-05-21 (post-rollback)

**Live system right now: stable.** It runs the **pre-Hermes Phase 1B** workflow
— direct Claude drafting, the version that passed T1–T6. The full Hermes
integration was built and deployed overnight, then **rolled back** after it
proved unstable under real traffic. Hermes is **paused, not deleted**.

- **Approval bot:** the "Dubriani Hermes" Telegram bot (`8861…`) — the bot swap
  was kept (it works; it wasn't the problem).

## 🔴 What happened — the incident

The Hermes integration (drafting via the bridge + refinement, rule capture,
triggers, health, autonomous mode, caps) was fully built and deployed. Under
real customer traffic it failed:
- Hermes `/draft` latency rose from ~10s to **20–50s+**; several calls exceeded
  the 120s bridge timeout → **502 → "Phase 1B — a step failed"**.
- Refinement (same bridge path) failed for the same reason.
- Suspected wrong-recipient drafts — consistent with the draft queue's
  pre-existing concurrency weakness (R10) amplified by execution pile-up.

**Decision:** rolled the live workflow back to pre-Hermes Phase 1B
(`scripts/rollback_workflow.py`). Hermes paused: bridge stopped + disabled,
Dubriani crons removed. The 53-node Hermes workflow is snapshotted at
`workflows/phase-1b-telegram.PRE-ROLLBACK-20260521_132234.json`.

## ⏳ Before Hermes can be re-deployed (do off the live path)

1. **Diagnose the drafting-latency regression.** Leading hypotheses:
   (a) `hermes chat -t memory` running multi-turn memory-tool loops that got
   slower as the profile's memory/session store accumulated; (b) `default`
   profile state bloat from hundreds of build-time drafts.
   Likely fix: drop `-t memory` (single-shot drafting) and/or prune profile
   state; **re-measure latency before any re-deploy**.
2. **R10 — draft-queue concurrency.** Pre-existing Phase 1B weakness (queue in
   n8n static data). Proper fix is the deferred Redis migration.
3. Re-run H7–H9 + the cap tests after a clean re-deploy.
